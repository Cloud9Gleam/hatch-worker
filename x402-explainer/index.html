Explain x402: How Autonomous Agents Pay for API Access

An autonomous agent that needs a weather forecast, a search result, or a

single database lookup faces a payment problem that humans rarely notice.

Human-oriented APIs are sold by subscription: create an account, add a

credit card, buy a monthly plan, and manage an API key. An agent that needs

exactly one call does not want a subscription, an account, or a card. It

wants to pay a fraction of a cent for that one call, in the same request

that asks for the data, and move on.

x402 is an open protocol that makes that possible. Developed by Coinbase

and released in 2025, it turns the long-dormant HTTP status code 402

("Payment Required") into a working machine-to-machine payment handshake.

Instead of accounts and keys, the client pays with a signed blockchain

authorization; instead of invoices, the server settles the payment through

a facilitator and returns the resource. This article explains the

protocol, the negotiation flow, and a concrete end-to-end example.

Sources: the x402 project site (https://www.x402.org/), the reference

implementation (https://github.com/coinbase/x402), the Coinbase Developer

Platform x402 documentation (https://docs.cdp.coinbase.com/x402), and

EIP-3009, the signed-authorization standard the payment scheme is built on

(https://eips.ethereum.org/EIPS/eip-3009).

The problem: accounts do not scale to agents

Traditional API billing assumes a durable relationship between buyer and

seller. The seller issues credentials, meters usage, and bills later. That

model breaks for agents in three ways. First, onboarding friction: an

agent cannot fill out a signup form or pass a card check for every service

it might touch once. Second, granularity: many agent tasks are worth a

cent or less, below the minimum viable charge of card networks. Third,

composability: an agent that chains ten services in one workflow would

need ten accounts, ten keys, and ten billing relationships.

Stablecoins on fast, low-fee chains solve the money part, but not the

protocol part. A server still needs a standard way to say "this resource

costs this much, payable this way," and a client needs a standard way to

answer "here is my payment, now serve the resource." x402 is that

standard, layered on plain HTTP so that any client or server can adopt

it without a new transport.

The three roles

Every x402 interaction involves three roles:

1. Client. The buyer, usually an autonomous agent. It holds a wallet

with stablecoins (USDC is the canonical example) and can sign

messages. It needs no account with the server.

2. Server (resource provider). The seller. It decides the price of

each resource and declares what payment it accepts. It does not touch

the blockchain directly.

3. Facilitator. A service that verifies the client's payment

authorization and submits the on-chain transfer. Facilitators are

interchangeable: a server can use a hosted facilitator, run its own,

or let the client suggest one. The facilitator is what keeps the

server's code simple — the server only ever talks HTTP.

A fourth party, the chain itself, settles the transfer. x402 launched on

Base, Coinbase's Layer 2 network, and support has since extended to

additional networks. The examples below use Base and USDC, the

best-documented combination.

The negotiation flow, step by step

The flow is deliberately boring: it is two HTTP round trips with

well-defined headers.

Step 1: the client asks without paying. The agent sends an ordinary

GET (or POST) to the resource, for example

GET /v1/premium-forecast?city=Osaka. It includes no payment header and

no credentials.

Step 2: the server answers 402 with payment requirements. Instead of

the resource, the server returns HTTP 402 and a JSON body describing

exactly what it accepts. The key fields are:

  • scheme: "exact", meaning the client pays precisely the quoted

amount (as opposed to an "upto" scheme, where the server may charge up

to a ceiling).

  • network: "base", the chain the payment settles on.
  • maxAmountRequired: the price in the token's smallest unit. USDC has

six decimals, so "10000" means $0.01.

  • asset: the token contract address (USDC on Base).
  • payTo: the server's receiving wallet address.
  • resource: the URL being purchased, so the payment cannot be replayed

against a different endpoint.

  • description and maxTimeoutSeconds: human-readable context and how

long the offer stands.

The client now has everything it needs to decide: is the price

acceptable, is the asset one it holds, is the payee the expected seller?

A careful client checks all three before signing anything.

Step 3: the client signs and retries. Under the "exact" scheme on

EVM chains, payment is an EIP-3009 transferWithAuthorization: the

client signs a message authorizing a transfer of a specific amount, to a

specific recipient, valid only within a time window, with a unique nonce.

Crucially, the client does not submit a blockchain transaction and pays

no gas — it only produces a signature. It base64-encodes the signed

payload and repeats the original request with an X-PAYMENT header

carrying it.

Step 4: the server verifies and settles through the facilitator.

The server forwards the payload to the facilitator's /verify

endpoint, which checks the signature, the nonce, the amount, the

recipient, and the validity window. If verification passes, the server

asks the facilitator to /settle: the facilitator submits the

authorization on-chain, the USDC moves from the client to the server,

and the facilitator returns a settlement receipt including the

transaction hash.

Step 5: the server serves the resource. The server returns the

requested data with an X-PAYMENT-RESPONSE header containing the

settlement receipt. The client can confirm on-chain that the exact

amount went to the exact payee, and both sides have a cryptographic

receipt for the exchange.

If verification fails — wrong amount, expired window, bad signature —

the server returns an error and serves nothing. No money moves without a

valid, server-checked authorization.

A concrete end-to-end example

Imagine an agent planning a delivery route that needs one premium

forecast for Osaka, priced at $0.01.

1. The agent requests /v1/premium-forecast?city=Osaka and receives

402: scheme exact, network base, maxAmountRequired "10000",

asset USDC on Base, payTo 0xServer…, maxTimeoutSeconds 60.

2. The agent checks the price against its budget ($0.01 is under its

$0.05 per-call ceiling), confirms it holds Base USDC, and notes the

60-second window.

3. The agent signs an EIP-3009 authorization: from its wallet, to the

server's address, value 10000, valid for the next 60 seconds, with

a fresh random nonce. It retries the request with the X-PAYMENT

header.

4. The server's facilitator verifies the signature and nonce, submits

the transfer, and returns a settlement receipt with the transaction

hash. The server responds 200 with the forecast and the receipt in

X-PAYMENT-RESPONSE.

5. The agent records the transaction hash, verifies the $0.01 transfer

on a Base explorer, and proceeds with route planning. Total

overhead: one extra round trip and one signature. No account, no

key, no subscription, no gas paid by the agent.

Notice what the agent never did: it never registered, never stored a

secret for this server, and never prepaid a balance that could strand

funds. Each call is self-contained, which is exactly the property an

agent fleet needs when it may call a service once and never again.

Why this matters, and where to be careful

For sellers, x402 turns any HTTP endpoint into a pay-per-use product:

one endpoint, one price, no billing system. For buyers, it turns every

API into something an agent can consume on first contact. That is why

the protocol has attracted directories and discovery layers where

agents browse priced endpoints the way humans browse app stores.

Careful clients still check the details. The quoted price in the 402

response is the only price that matters — compare it with the advertised

price before signing. Confirm the asset contract is the genuine USDC

contract, not an imitation token with the same symbol. Respect the

validity window: an authorization that lives too long can be replayed

within its window, so short windows and fresh nonces are good practice.

And remember that settlement is only as trustworthy as the facilitator

path: the on-chain transaction hash in the receipt is the proof, so

verify it rather than trusting the header alone.

The bigger picture

x402 does not replace subscriptions for heavy, repeated use — a

standing relationship with volume pricing still makes sense there. What

it replaces is the assumption that a relationship must exist before the

first byte flows. By putting price discovery, payment, and settlement

inside the HTTP exchange itself, it gives autonomous agents something

they have never had: the ability to pay for exactly what they use, from

any seller, on first contact, without asking a human to sign up first.
